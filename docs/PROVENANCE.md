# 开发流程与原创性证据（PROVENANCE）

本文件记录 `scitrace` 的开发流程、隔离纪律、**污染事件**与验证手段。
它的目的是让"本项目代码为独立编写"这一主张**可被第三方核查**，而不是一句自述。

**我们不使用它的方式**：不作为代码来源，不作为文本来源，不作为依赖。

## 2. 洁净室纪律（本项目的实际标准）

严格的"洁净室"（clean room）要求**两个人**：一人读原始实现写规格，另一人只读规格写实现，
两人之间无信息泄漏。本项目是单人开发，**无法满足该标准**。因此我们采用一个**可核查的
弱化标准**，并如实标注其边界：

> **标准**：独立重实现（independent reimplementation）。
> 全部代码与文本由本项目作者编写，**未复制**上游任何受著作权保护的表达；
> 作者对上游的接触范围被完整记录（§3），并通过机械化审计（§4）验证无文本复制。

### 纪律条款

| # | 条款 |
| --- | --- |
| R1 | `docs/SPEC.md` 是实现的唯一依据。规格冻结后，实现阶段不再阅读上游源码 |
| R2 | 上游仓库与本项目仓库**不放在同一工作目录**（本机上分别为 `/home/wby/PaperQA` 与 `/home/wby/MyPaperQA`） |
| R3 | 绝不从上游复制代码片段、注释、docstring、Prompt、文档句子——包括"改写式搬运" |
| R4 | 不引入上游及其同族依赖；不使用上游标识符（`PaperQA` / `pqa` / `pqac`） |
| R5 | 每次提交前运行 `tools/similarity_audit.py`，报告入库（`docs/AUDIT.md`） |
| R6 | 发现任何疑似污染，立即登记到 §3，并重写相关实现 |

## 3. 污染记录（Contamination Log）

**这是本文件最重要的一节。** 如实记录接触范围，才能让外部评估者判断风险边界。

### E1 — 需求分析阶段的结构性勘察（2026-02）

在编写 SPEC 之前的需求分析中，为评估可行性与工作量，执行了以下**只读**操作：

| 操作 | 接触内容 | 风险 |
| --- | --- | --- |
| 目录/文件枚举、行数统计 | 文件路径、模块划分、代码规模 | 低（事实性信息） |
| `git remote -v` / `git log` / `git status` / `git diff` | 仓库元信息、作者本地的中文注释改动 | 低 |
| `grep "^(class\|def\|async def)"` 于 `docs.py`、`types.py`、`settings.py`、`llms.py`、`readers.py`、`utils.py`、`agents/*` | **类名、函数名、方法签名清单** | 中（接口命名可能被无意识沿用） |
| 读取 `core.py` 第 1–120 行**全文** | JSON 容错解析函数的实现细节 | **高** |
| 读取 `prompts.py` 第 1–60 行**全文** | 若干 Prompt 字符串原文 | **高** |
| 读取 `LICENSE`、`CITATION.cff`、`pyproject.toml` | 许可与依赖清单 | 低 |

**结论**：本次项目**不是**严格洁净室，`core.py` 与 `prompts.py` 的接触构成实质污染风险。

### 缓解措施（已执行 / 待执行）

| 风险面 | 缓解 | 状态 |
| --- | --- | --- |
| Prompt 文本 | `prompts/` 下的全部提示词从零重写，采用本项目自己的哨兵短语、引用格式与说明顺序；哨兵 `NOT_APPLICABLE` / `INSUFFICIENT_EVIDENCE` 与上游表述无关 | 待实现（M5） |
| JSON 容错解析 | SPEC §3.7 规定了本项目自定的四步降级链（直接解析 → 剥围栏 → 剥思维链 → 括号配平截取 → 正则提取），**不使用**上游的正则改写策略 | 待实现（M4） |
| 接口命名 | SPEC §2.1 采用自定术语（`Source`/`Fragment`/`Evidence`/`Session`/`EvidenceKey`），与上游命名体系不同 | 已完成 |
| 无意识重叠 | `tools/similarity_audit.py` 逐提交扫描 8-gram / 字符串字面量 / 逐行复制 | 脚本已就绪（见 `docs/AUDIT.md`） |
| 依赖与标识符 | 审计脚本第 4 项硬性阻断 | 已就绪 |

> **为何不隐藏这些接触**：审计脚本本身就是为了让"是否复制"变成可测量的客观问题。
> 一份如实记录的接触清单 + 一份通过阈值的机械审计，比一句"我完全没看过"更可信——
> 后者既无法验证，也不是事实。

## 4. 机械化验证

### 4.1 审计脚本

```bash
python tools/similarity_audit.py \
    --target /home/wby/MyPaperQA \
    --reference /home/wby/PaperQA \
    --report docs/AUDIT.md
```

比对基准通过 `git -C <reference> show HEAD:<path>` 读取上游**跟踪文件的原始版本**，
从而排除作者本地的中文注释改动与未跟踪文件。

### 4.2 检查项与阈值

| # | 检查项 | 阈值 | 意义 |
| --- | --- | --- | --- |
| 1 | token 8-gram containment（含注释与字符串） | 单文件 ≤ 5%，整体 ≤ 2% | 无代码/注释搬运 |
| 2 | 逐行精确复制（≥12 字符的非空行） | 0 命中 | 无逐行复制 |
| 3 | 字符串字面量相似度（≥20 字符，`difflib`） | 任意一对 < 0.6 | 无 Prompt 搬运 |
| 4 | 禁用依赖与标识符 | 0 命中 | 无依赖/命名污染 |
| 5 | 与上游资产 SHA-256 相同的文件 | 0 命中 | 无测试数据搬运 |

### 4.3 这套验证**不能**证明什么

必须说清楚，否则就是过度宣称：

- 它**不能**证明"思想独立"——方法、流程、架构思想来自公开论文，这是有意为之且公开声明的；
- 它**不能**排除"读过后凭记忆重写"的情况——只能保证结果层面无可测量的文本重叠；
- 它**不能**替代法律意见。

**可以声称的**：本项目代码由作者编写，未复制上游受保护的表达；设计范式来源已公开署名。

## 5. 决策日志

| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-02 | 选择"洁净室重写 + 原创增量"而非"fork 改名" | fork 改名违反 Apache-2.0 §4 且无法声明原创 |
| 2026-02 | 公开在 README/NOTICE 中署名 PaperQA2 的方法来源 | 署名不削弱代码著作权；隐瞒才是致命风险 |
| 2026-02 | 项目命名 `scitrace`，CLI `stc`，配置目录 `~/.scitrace` | 规避上游商标（Apache-2.0 §6） |
| 2026-02 | 自定义术语体系（Source/Fragment/Evidence/Session/EvidenceKey） | 降低接口命名层面的无意识沿用 |
| 2026-02 | 引用键格式 `ev-<8hex>`，确定性生成 | 与上游 `pqac-` 方案完全区分，且可复现 |
| 2026-02 | 中文全文检索采用 bigram + whitespace tokenizer | 免分词依赖、对中文/中英混合语料都可用的原创工程选择 |
| 2026-02 | 首版砍掉多模态富化/ClinicalTrials/Zotero/OpenReview | 聚焦核心闭环；这些部分最容易被误认为复现上游 |
| 2026-02 | 自研 Agent 运行时，不依赖 `fhaviary`/`ldp`/`fhlmi` | 切断与上游最深的一层工程依赖，同时构成原创增量 ① |
